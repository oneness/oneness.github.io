* Voice and Tone

- **Conversational but deliberate.** Write like talking to a fellow
  engineer over coffee, not delivering a keynote. Short, clear
  sentences. No showing off.
- **Philosophy-driven, practically grounded.** Every post connects an
  abstract principle to real code, real workflows, real decisions.
  Never stay in the clouds without landing in something concrete.
- **Honest and measured.** Acknowledge trade-offs. Say "I don't think"
  and "in my experience." Avoid dogmatic absolutism. Use disclaimers
  ("this is not a flame war") when the topic invites them.
- **First-person, experiential.** Everything comes from what has been
  actually done, built, or lived through. Share real elisp, real
  shell scripts, real flake.nix files. No hypothetical examples when
  real ones exist.
- **Thematic repetition is a feature.** Return to core ideas
  (simplicity, one source of truth, inspectability, reproducibility,
  small primitives) across different domains and let the pattern speak
  for itself.

* Structure Patterns

- **Short posts** (early era): Hook -> context -> code example -> brief
  takeaway. Often under 500 words. Example: "less is literally more,"
  "curl to the rescue."
- **Tutorial posts**: Motivation -> setup -> working code -> usage tips.
  Example: "Why Eshell" series, "OpenBSD 7 Xfce Desktop."
- **Essay posts** (later era): Opening thesis -> layered argument with
  concrete examples -> broader reflection -> closing that ties back to
  the opening. Often 1500-3000 words. Example: "Oneness is All You
  Need," "Why I Love NixOS," "Emacs as a Programmable Workbench,"
  "Why I Love Agent Pi."
- **Conference notes**: Category-grouped takeaways with "AHA" moments.
  Example: Strange Loop notes.

Footnotes are used in essay posts to link sources, prior posts, and
clarifications without cluttering the main text.

* Formatting Conventions

- Org-mode source files with =#+title=, =#+date=, =#+description=,
  and =#+filetags=.
- Date format: =<YYYY-MM-DD Day>=.
- Code blocks use =#+begin_src <lang>= with language tag.
- Bold for tool names and key terms on first mention: *Emacs*, *Nix*,
  *cURL*.
- Internal cross-links use full birkey.co URLs.
- External links use Org link syntax: =[[url][description]]=.
- Quotes use =#+BEGIN_QUOTE= / =#+END_QUOTE=.
- File naming: =YYYY-MM-DD-slug-with-dashes.org=.

* Recurring Themes

1. **ETC (Easy To Change)** — the grounding principle for engineering
   decisions.
2. **Oneness** — one source of truth, one obvious path, one clear
   owner per layer.
3. **Reproducibility and determinism** — Nix, declarative systems,
   pinned inputs.
4. **Small durable primitives over feature bloat** — Unix, Emacs,
   Pi/OneLoop. Four tools: read, write, edit, bash.
5. **Inspectability and visibility** — keeping the work legible,
   reviewable, verifiable.
6. **LLM era as amplifier** — generated code is abundant,
   understanding is not. Agents compound ambiguity if not harnessed
   with discipline.
7. **Self-documenting systems** — tools that explain themselves
   (Emacs, Makefile help targets, Pi extension docs).
8. **The workbench model** — Emacs as a unified programmable
   environment. Buffers as working surfaces.
9. **Security and privacy as defaults** — OpenBSD, random MAC
   addresses, HTTPS-only, no unnecessary exposure.
10. **Transmittable vs untransmittable knowledge** — some things can
    only be learned from masters in close proximity (Strange Loop,
    craftsmanship).

** TODO [2026-10-03] Everything I Build Around the LLM Becomes a Distraction
   - Status: in review (moved to =posts/=, HTML not yet generated)
   - Summary: Notes from a year of using LLMs for software
     development, titled for the recurring shape of the experience —
     every piece of machinery built to work with the model (context
     engineering, compaction handoff, customizing a third-party agent)
     kept becoming its own distraction, while what actually helped was
     smaller and simpler than expected. Underneath that churn, the
     methodology and strategies keep changing, but the core of the
     problem and the core mental model of understanding it has stayed
     the same. Walks the journey in order: confined problems
     (refactoring, simplifying modules), the context engineering rabbit
     hole, context management and compaction, trying to understand a
     third-party coding agent, skills, spec driven development
     drifting into documentation explosion, scripts instead of prose,
     and starting with an executable prototype — the single HTML file —
     as the thing currently paying off best.
   - Key points:
     - The landscape changes very fast; a lot of trendy things turned
       out to be more signal than real entropy (a separate post to
       come)
     - The one takeaway: use it, see it, understand the benefit, the
       trade-offs, and what you are losing — then adapt
     - LLM helps, but used carelessly it produces more content,
       features, and code than you have understanding of, with no
       orthogonal consistency for the complexity of the problem
     - Confined problems work well: the problem is already solved,
       refactoring is a well suited shape of task
     - Context is critical; grab search (syntactic or semantic) was
       where we started, from the code base, the web, and literature
     - Context engineering is a dark art: methods degrade on model
       updates, evals force endless refinement, and the quality does
       not improve in proportion to the time invested
     - Ultimately: starting over, no amount of prompting or extra
       context fixes it
     - Context compaction: no deterministic way to summarize and
       hand off; manual summarization plus verification is what
       actually works now, and on the client side it is a drag on
       productivity
     - Third-party coding agents become too complex to understand;
       you cannot tell what the current prompt or in-memory context
       is. Master the tool you are using, or write your own
     - Skills furnish context on demand and are dynamically loaded, so
       they don't cover the context the whole time. Better ROI than
       not, and you can turn an ad hoc prompt you've been repeating
       into a well structured skill and get better results. But they
       are not a deterministic instruction set, more of an advisory
       the LLM more or less follows
     - Spec driven development starts well then drifts; specs should
       be sparing and high level, with detail in executable code
     - For repetitive work, ask for an executable script plus a skill
       that uses its output
     - Always start with an executable prototype of the actual flow,
       often a single self-contained HTML file, as a blueprint for the
       real app
